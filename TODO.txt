		looking closer at how mypy handles this situation I find the following:
			1) @overload methods are typing only, they must not have bodies
			2) @overloads must be matched exactly. In the above example, mypy
				rejects it because neither overload takes A|B
		
		I can only draw the conclusion that metalpy's function overloading is a little different
			than Python and I think metalpy's greater flexibility is a bonus, but now
			I have to figure out how to handle this conflict.
		
		To make a long story short, the real issue with this code is that its possible that
		either or none of the functions could match, depending on the types of x and y.
		So, what to do when there's no match?
		
		I think its possible to make this a compile time error, but its going to be a little
		complicated. Maybe this is where Claude's suggestion about cartesian products
		comes into play? In the runtime disambiguation, if the check for foo(A,A) fails,
		then we know that (x:A|B,y:A|B) is either (x:B,y:A|B) or (x:A|B,y:B). by tracking
		all possible type states, we can figure out if there's a possibility that no
		types will match during a runtime dispatch and therefore kick it out as a compile error.
		
		Let's look at an example that should compile:
		
		class A: pass
		class B: pass
		
		def foo( v: A, w: A ) -> None:
			pass
		
		def foo( v: B, w: B ) -> None:
			pass
		
		def foo( v: A|B, w: A|B ) -> None:
			pass
		
		def main() -> None:
			x: A|B
			y: A|B
			foo( x, y )
			return
		
		When checking foo(A,A):
			(x:A|B,y:A|B) -> either x isn't A or y isn't A, this produces 2 states:
				if x != A:
					next (x:B,y:A|B)
				elif y != A:
					next (x:A,y:B)
				else:
					schedule foo(A,A) (it is reachable)
		
		When checking foo(B,B):
			we are tracking 2 states now, which becomes 4 states (but 2 get eliminated immediately)
			(x:B,y:A|B) ->
				if x != B:
					drop (this is impossible)
				elif y != B:
					next (x:B,y:A)
				else:
					schedule foo(B,B) (it is reachable)
			(x:A|B,y:B) ->
				if x != B:
					next (x:A,y:B)
				elif y != B:
					drop (this is impossible)
				else:
					schedule foo(B,B) (it is reachable)
		When checking foo(A|B,A|B):
			we still only have 2 states, need to check both:
			(x:B,y:A) ->
				if x != A|B:
					drop (this is impossible)
				elif y != A|B:
					drop (this is impossible)
				else:
					schedule foo(A|B,A|B) (it is unavoidable)
			(x:A,y:B) ->
				(we don't even analyze this because the first pattern matched unconditionally
		
		Note the above logic is how I worked through the type checking, but the runtime logic
		will be simpler:
		
		if instanceof( x, A ) and instanceof( y, A ):
			foo[A,A]( x, y )
		elif instanceof( x, B ) and instance( y, B ):
			foo[B,B]( x, y )
		else:
			foo[A|B,A|B]( x, y )

		class A: pass
		class B: pass
		def foo( v: A, w: A ) -> None:
			pass
		def foo( v: B, w: B ) -> None:
			pass
		def main() -> None:
			x: A|B
			y: A|B
			foo( x, y )
			return
		
		checking foo(A,A):
			(x:A|B,y:A|B) ->
				if x != A:
					next (x:B,y:A|B)
				elif y != A:
					next (x:A,y:B)
				else:
					schedule foo(A,A) (it is reachable)
		
		checking foo(B,B):
			(x:B,y:A|B) ->
				if x == B -> (x:B,y:A|B)
					if y == B -> (x:B,y:B)
						schedule foo(B,B)
					else -> (x:B,y:A)
						next (x:B,y:A) *********************
				else -> (x:_,y:A|B)
					drop (this is impossible)
			(x:A,y:B) ->
				if x == B ->
					drop (this is impossible)
				else -> (x:A,y:B)
					next (x:A,y:B) **************************

		evaluating the last possible function, we are still have one or more
		unmatched parameter type possibilities:
			(x:B,y:A),
			(x:A,y:B)

		The CFG will need to track unions as Union|UnionView

		class TaggedUnion( Type ):
			...
			def view_is_type( self, type: Type ) -> UnionView|None:
				leaves = self.leaves()
				if type not in leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				return UnionView( union = self, types = set([ type ]))

			def view_not_type( self, type: Type ) -> UnionView|None:
				leaves = self.leaves()
				if type not in leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				leaves.remove( type )
				return UnionView(
					union = self,
					types = leaves,
				)

		class UnionView( Type ):
			union: TaggedUnion
			leaves: set[Type]

			def view_is_type( self, type: Type ) -> UnionView|None:
				if type not in self.leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				return UnionView( union = self.union, leaves = set([ type ]))

			def view_not_type( self, type: Type ) -> UnionView|None:
				if type not in self.leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				new_leaves = self.leaves.clone()
				new_leaves.remove( type )
				return UnionView( self.union, new_leaves )

		as it passes through a match or ifelse tree

		def foo( x: int|str|bytes ) -> None:

			elif x is str: # UnionView( union = int|str|None, leaves = [ str, bytes ]).view_is_type(str) -> UnionView( union = int|str|bytes, leaves = [ str ])
				print( x ) # translates to print( x.v_str )
			# the false branch of the elif above triggers type translation: x`` = UnionView(...).view_not_type(str)
			else: # at this point we have a single-type UnionView
				print( x ) # translates to print( x.v_bytes )

			# at this point, we've exited the if-else-chain, the UnionView is discarded and x is int|str|bytes again

			# the next example is a wrinkle on the above logic.

			if x is int:
				return

	opportunistic union emission
		when a union is used, we need to generate IR to reach through it to the
			underlying code.
		note that we disambiguate directly in generated code when doing things directly
		with the union, but if we call a method on a union object, we attempt to auto-generate
		a method that does the disambigutation for us. If the method isn't available on all types
		or has incompatible function signatures, it will be caught when it gets resolved and lowered,
		so we don't have to do any special type checking when actually generating the automatic
		union methods

		For this code example, assume:
			@union
			class IntStr:
				v_int: int
				v_str: str
		
		P.S. this is *not* a specification for how to name automatic unions in C, that is not
			in scope for the lowering stage.
		P.P.S. through the examples below, I use TAG_INT and TAG_STR, this is not a specification,
			just a placeholder for the actual values that will be generated to represent each member

		this:
			a: IntStr = 'foo'
		becomes:
			a = IntStr.v_str( 'foo' )
		this:
			if isinstance( a, int ):
				print( a )
		becomes:
			if a.tag == IntStr.TAG_INT:
				print( a.v_int )
		this:
			print( a )
		becomes:
			print( a.__str__() )
		and auto-generates the following wrapper if it doesn't already exist:
			class IntStr:
				def __str__( self ) -> str:
					match self.tag:
						case IntStr.TAG_INT:
							return self.v_int.__str__()
						case IntStr.TAG_STR:
							return self.v_str.__str__()
						case _:
							sys.panic( 'system invariant, invalid union tag' )
