		class TaggedUnion( Type ):
			...
			def view_is_type( self, type: Type ) -> UnionView|None:
				leaves = self.leaves()
				if type not in leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				return UnionView( union = self, types = set([ type ]))

			def view_not_type( self, type: Type ) -> UnionView|None:
				leaves = self.leaves()
				if type not in leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				leaves.remove( type )
				return UnionView(
					union = self,
					types = leaves,
				)

		class UnionView( Type ):
			union: TaggedUnion
			leaves: set[Type]

			def view_is_type( self, type: Type ) -> UnionView|None:
				if type not in self.leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				return UnionView( union = self.union, leaves = set([ type ]))

			def view_not_type( self, type: Type ) -> UnionView|None:
				if type not in self.leaves:
					raise CompilationError( f"redundant type check, {type!r} can't be in {leaves!r}" )
				new_leaves = self.leaves.clone()
				new_leaves.remove( type )
				return UnionView( self.union, new_leaves )

		- bare CUnion (no paired discriminant, unlike a TaggedUnion's own
			.tag or Result's hand-rolled tag+payload pairing) has no general,
			structural way to know which member is live, so the destructor's
			cascading-decref walk deliberately skips it rather than risking a
			double-free/decref-garbage on a member that isn't actually set.
			Real open design question for whoever needs RC-class content
			inside a bare @cunion (e.g. a bare Result[SomeRCClass,E] embedded
			BY VALUE as another RCClass's own field) - could also just become
			a compiler error disallowing RC content in a bare @cunion with no
			discriminant at all, simpler now that ResultPayload no longer
			needs a name-based exemption.
		- linking: no linker pragmas/flags for an @extern function's own
			declared library. (Wiring a module's __metalpy_init_<global>
			functions into the real process entry point is done - see
			PLAN_GLOBAL_INIT.md.)
		- real lib/ end-to-end verification (actually compiling lib/sys.py,
			lib/windows/kernel32.py, lib/builtins/__init__.py etc. as they
			exist today, rather than the self-contained fixtures the emitter
			test suite uses) is still open, blocked partly on lib/sys.py's
			own still-evolving File I/O design (see sys._BufferedStream.write() notes
			above) and partly on specific known gaps surfaced by real compile
			attempts: a missing sys.alloc[T] forward declaration, Result[_,
			ZeroDivisionError] not being scheduled for panic-wrapped division,
			and a missing argument in lib/sys.py's WriteFile call.
		- a generic class's own __init__ is never monomorphized when reached
			through plain ClassName(...) construction inside a helper
			function (confirmed via a non-Result generic RCClass repro).

list class
	first-draft implementation

	list[T] is now thread-safe: it's a FastLock-guarded wrapper (lib/
		builtins/__list.py) around UnsafeList[T], which is the old
		unsynchronized implementation, kept as an explicit opt-in escape
		hatch (same positional/order-preserving semantics, no lock).
		FastList[T] is unrelated (swap-and-pop erase, stable IDs, not
		insertion-order-preserving) and untouched by this. Verified via
		real compile+run concurrency stress tests in emitter_c_test.py's
		ListThreadSafetyTests (8 producers pushing known values, 8
		producers + 1 concurrent consumer draining, and an RC-element
		variant confirming no leak/double-free) - repeat-run 10x via
		PowerShell with zero flakiness.

	slice[T] (builtins/__init__.py) is a borrowed view (_ptr/__len, plus a
		real RC lifecycle now - see below) - RESOLVED for list[T]: slice[T]
		is a plain (non-@cstruct) generic RCClass whose __init__/__del__
		atomically increment/decrement an optional __borrow_addr pointer
		(RAII, tied to the slice's own RC lifetime), replacing the old
		manual, unpaired-call-prone list[T].borrow_slice()/release_borrow().
		list[T][a:b] (or .as_slice()) wires this to list[T]'s own __borrows
		counter, which append/insert/erase_at/pop/clear already check and
		refuse to proceed against while nonzero - so a list[T]-sourced
		slice[T] genuinely blocks concurrent mutation for as long as it's
		alive, verified via a real cross-thread stress test
		(emitter_c_test.py's slice_syntax_blocks_concurrent_mutation_and_
		unblocks_on_del). STILL OPEN for UnsafeList[T] specifically
		(deliberately unguarded, single-owner by design - no __borrows field
		at all, so UnsafeList[T][a:b]/.as_slice() always pass borrow_addr=
		None): a function that snapshots a slice's .len() once and then
		indexes it across multiple statements (e.g. str.concat's own
		`for i in range(count): part = parts.get_unchecked(i)` loop, fed by
		UnsafeList[str].as_slice()) is reading through a pointer that
		another thread could in principle be mutating or freeing
		concurrently - not applicable to UnsafeList's own real callers today
		(all single-threaded), but still a real gap if that assumption is
		ever violated. Fixing THAT for real would mean giving UnsafeList[T]
		its own borrow tracking too (a real design/perf tradeoff - UnsafeList
		exists specifically to skip that cost) or real ownership/borrow-
		checking at the type level - same unsolved problem as incref/decref/
		move[T] above, not a one-off gap in str.concat specifically. Element-
		level RC correctness (as opposed to the view/buffer question above)
		is unrelated and already fine: get_unchecked() returns an owned,
		correctly-refcounted ELEMENT for RC T on its own (increfs
		internally), regardless of which flavor of slice[T] it came from.

	generic list[T] method calls (e.g. xs.append(...)) used to fail in the
		old emitter.py's _transpile_call ("could not resolve receiver class
		'list[i32]' for .append(...)") - that emitter no longer exists
		(replaced by emitter_c.py), and generic-class-method monomorphization
		has since been implemented for the new pipeline, but this specific
		case (a monomorphized generic list[T] instantiation's own method
		resolution) hasn't been re-verified against it yet - needs a real
		compile-through-clang check before this can be considered fixed

dict class
	first-draft implementation, WIP - real-compile-and-run tested
		(emitter_c_test.py's DictTests), __getitem__/__setitem__/
		__contains__/__delitem__ all implemented (RawDict.remove_entry adds
		real removal, no longer append-only - see __RawDict.py's own module
		docstring), key_at/value_at for positional access, still no
		iteration (keys()/values()/items()/__iter__)

	set[T] (lib/builtins/__set.py) is a thin wrapper around dict[T, bool],
		built to exercise the above - add/discard/remove/__contains__/
		__len__, plus __getitem__(idx: usize) forwarding to key_at (makes
		`for x in my_set:` work via the existing indexable for-loop
		protocol). No set literal syntax, no set algebra
		(union/intersection/...), no `x in my_set`/`del my_set[x]` operator
		sugar (same underlying gaps as dict[K,V]'s own __contains__/
		__delitem__ - named methods only, must be called directly).

	dict[K,V] is now thread-safe, same split as list[T]: a FastLock-
		guarded wrapper (lib/builtins/__init__.py) around UnsafeDict[K,V],
		the old unsynchronized implementation kept as an explicit opt-in
		escape hatch. dict[K,V].with_lock(body) takes the raw
		UnsafeDict[K,V] as body's own argument (unlike list[T]'s no-arg
		with_lock) so a compound read-modify-write can be done as one
		atomic critical section without deadlocking on dict[K,V]'s own
		non-reentrant lock. Verified via real compile+run concurrency
		stress tests in emitter_c_test.py's DictThreadSafetyTests (8
		threads inserting disjoint keys, 8 threads doing a contended
		with_lock-guarded increment on the SAME key, and an RC-key/RC-
		value variant checking for no leak/double-free) - repeat-run 10x
		via PowerShell with zero flakiness.

		Found and fixed a real, general compiler bug along the way:
		monomorphize.py's substitute_type_params never substituted type
		params through a ClosureType's own arg_types/return_type (it
		special-cased CallableType for this - see PLAN_CALLABLE.md - but
		ClosureType, added later for bound-method closures, was never
		added to the same branch). This left ANY generic class with a
		Closure[...]-typed method parameter mentioning that class's own
		type params (e.g. dict[K,V].with_lock's own
		body: Closure[[UnsafeDict[K,V]],None]) generating a call to an
		unmonomorphized, never-defined closure-alloc symbol once actually
		called from monomorphized code - not dict-specific, would have hit
		any future generic class doing the same thing.
